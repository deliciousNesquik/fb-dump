# fb-dump

[English](README.md) · **Русский**

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Releases](https://img.shields.io/github/v/release/deliciousNesquik/fb-dump?sort=semver)](https://github.com/deliciousNesquik/fb-dump/releases)
[![Firebird 3/4/5](https://img.shields.io/badge/Firebird-3%20%7C%204%20%7C%205-orange)](https://firebirdsql.org/)

`fb-dump` читает схему работающей базы данных **Firebird** и записывает её в виде дерева
файлов `.sql` — **один объект, один файл**, где файл содержит *полное* определение
объекта: DDL, ограничения, комментарии и гранты.

Инструмент делает одно дело. Он читает системный каталог через
[`firebird-lib`](https://pypi.org/project/firebird-lib/) (без `isql`, без разбора текста),
пишет детерминированный вывод и либо создаёт полное дерево, либо не создаёт ничего.

## Быстрый старт

```bash
export ISC_USER=SYSDBA ISC_PASSWORD=masterkey          # стандартные переменные клиента Firebird

fb-dump -d localhost:employee -o schema                  # полный дамп в ./schema
fb-dump -d localhost:employee --list                     # что там внутри?
fb-dump -d localhost:employee CUSTOMER                   # один объект, выведенный в stdout
fb-dump -d localhost:employee CUSTOMER -o schema         # или обновить дерево
fb-dump -d localhost:employee > employee.sql             # вся схема в виде одного скрипта
```

Дамп выглядит так:

```text
schema/
├── .fb-dump.toml               <- структура дерева (и маркер безопасности fb-dump)
├── DATABASE.sql                <- диалект, кодировка по умолчанию, права доступа на уровне базы данных
├── 01_ROLES/
├── 04_GENERATORS/
├── 06_DOMAINS/
├── 07_TABLES/
│   └── CUSTOMER.sql            ← CREATE TABLE + constraints + comments + grants
├── 08_INDICES/
├── 10_VIEWS/
├── 11_PROCEDURES/
└── 13_TRIGGERS/
```

## Установка

### Готовые бинарники (без установленного Python)

Скачайте необходимый под вашу платформу исполняемый файл со страницы [Releases](https://github.com/deliciousNesquik/fb-dump/releases).

```bash
chmod +x fb-dump-linux-x64 && ./fb-dump-linux-x64 --help
```

Бинарнику всё равно нужна **клиентская библиотека Firebird** (`fbclient.dll` / `libfbclient.so` /
`libfbclient.dylib`) во время работы — её загружает `firebird-driver`. Она есть везде, где
установлен клиент или сервер Firebird. На macOS бинарник не подписан; один раз разрешите его в
*Системные настройки → Конфиденциальность и безопасность*.

### Из исходников

```bash
git clone https://github.com/deliciousNesquik/fb-dump.git && cd fb-dump
uv run fb-dump --help            # uv создает окружение на основе pyproject.toml
```

Python 3.11+, зависимости `firebird-driver` и `firebird-lib` (2.x). Без `uv`: установите пакет
в виртуальное окружение и запускайте `fb-dump` или `python -m fb_dump`.

## Параметры подключения

Флаги имеют приоритет над переменными окружения. Пароль **никогда** не принимается из
командной строки (он утёк бы через `ps`); задайте `ISC_PASSWORD` в окружении.

| Флаг | Переменная окружения | По умолчанию | Значение |
| --- | --- | --- | --- |
| `-d`, `--database DSN` | `FB_DATABASE` | *обязателен* | Алиас, путь к файлу или `HOST:ALIAS_OR_PATH`. |
| `-u`, `--user USER` | `ISC_USER` | умолчание драйвера | Пользователь базы данных. |
| — | `ISC_PASSWORD` | — | Пароль. |
| `-r`, `--role ROLE` | `FB_ROLE` | — | SQL-роль для подключения. |
| `--charset CS` | `FB_CHARSET` | `UTF8` | Кодировка подключения (см. [Кодировки](#кодировки)). |
| `--fallback-charset CS` | — | — | Вторая кодировка для метаданных в смешанных кодировках. |

`ISC_USER` и `ISC_PASSWORD` — стандартные переменные, которые клиентская библиотека Firebird
читает сама; `fb-dump` лишь передаёт их дальше. `fb-dump` не читает файлы `.env` — используйте
оболочку (`set -a; . ./.env; set +a`), `direnv` или `uv run --env-file .env fb-dump …`.
Переменные показаны в `.env.example`.

## Режимы

**Полный дамп** — без имён объектов. Читает всю схему и записывает полное дерево
(`--out`) либо печатает каждый файл в stdout в порядке каталогов, с заголовком
`-- ===== path =====` перед каждым. Дерево заменяется целиком и только если прочитан
каждый объект (см. [Гарантии](#гарантии)).

```bash
fb-dump -d DSN -o schema
fb-dump -d DSN -o schema --layout plain          # Директории без номеров
fb-dump -d DSN > schema.sql
```

**Точечная выгрузка** — одно или несколько имён объектов. Имена сопоставляются без учёта
регистра; имя, встречающееся в нескольких категориях, даёт несколько файлов, если `--type`
не сужает выбор. Без `--out` SQL печатается в stdout; с `--out` перезаписываются только
затронутые файлы (ничего не удаляется — вычищать устаревшее должен полный дамп).
Используется собственная раскладка дерева.

```bash
fb-dump -d DSN ACCOUNT                        # каждый ОБЪЕКТ (таблица, процедура…)
fb-dump -d DSN ACCOUNT --type table           # просто таблица
fb-dump -d DSN ACCOUNT CALC_TOTAL -o schema   # обновляет два объекта в дереве
```

**Список** — `--list` печатает `type<TAB>name` для каждого объекта, отсортировано по
категории, затем по имени:

```bash
fb-dump -d DSN --list                         # все
fb-dump -d DSN --list --type procedure        # одна категория: процедуры
fb-dump -d DSN --list | cut -f2 | sort        # pipe-дружелюбен
```

## Опции

| Опция | Где действует | Описание |
| --- | --- | --- |
| `NAME…` | точечный | Имена объектов. Их наличие включает точечный режим. |
| `-o`, `--out DIR` | полный, точечный | Писать файлы сюда, а не в stdout. |
| `--layout PRESET\|FILE` | полный, точечный | `numbered` (по умолчанию), `plain`, `flat` или TOML-файл. |
| `--print-layout` | — | Напечатать действующую раскладку в виде TOML и выйти (без подключения к базе). |
| `--allow-partial` | полный | Записать дерево, даже если часть объектов не удалось выгрузить. |
| `--force` | `--out` | Использовать непустой каталог, в котором нет `.fb-dump.toml`. |
| `--type TYPE` | точечный, список | Ограничиться одной категорией. |
| `--list` | список | Перечислить объекты и выйти. |
| `-q`, `--quiet` / `-v`, `--verbose` | все | Только ошибки / отладочный вывод (в stderr). |
| `--version`, `-h` | — | |

**Значения `--type`:** `table`, `index`, `view`, `procedure` (`proc`), `function`,
`external-function` (`udf`), `trigger`, `exception`, `domain`, `generator` (`sequence`),
`role`, `package`, `collation`.

Диагностика уходит в **stderr**; в stdout — только данные.

## Что содержит файл

Каждый файл — объект целиком, в таком порядке: определение, комментарии, гранты.

| Категория | Определение | Также в файле |
| --- | --- | --- |
| роль | `CREATE ROLE` | `COMMENT ON ROLE`; членство в роли: `GRANT role TO user [WITH ADMIN OPTION]`, `GRANT DEFAULT role TO …` |
| сортировка (collation) | `CREATE COLLATION` | комментарий |
| внешняя функция (UDF) | `DECLARE EXTERNAL FUNCTION` | комментарий, `GRANT EXECUTE` |
| генератор | `CREATE SEQUENCE` | комментарий, `GRANT USAGE`. **Без текущего значения** — это данные, а не схема. |
| исключение | `CREATE OR ALTER EXCEPTION` | комментарий, `GRANT USAGE` |
| домен | `CREATE DOMAIN` | комментарий |
| таблица | `CREATE TABLE`, затем каждое ограничение отдельным именованным `ALTER TABLE … ADD CONSTRAINT` (PK, UNIQUE, CHECK, FK) | комментарии к таблице и столбцам, `GRANT SELECT, INSERT, UPDATE (cols) …` |
| индекс | `CREATE INDEX` (+ `ALTER INDEX … INACTIVE`, если индекс неактивен) | комментарий |
| функция | `CREATE OR ALTER FUNCTION` | комментарий, `GRANT EXECUTE` |
| представление | `CREATE OR ALTER VIEW` | комментарии к представлению и столбцам, гранты |
| процедура | `CREATE OR ALTER PROCEDURE` | комментарии к процедуре и параметрам, `GRANT EXECUTE` |
| пакет | `CREATE OR ALTER PACKAGE` + `RECREATE PACKAGE BODY` | комментарий, `GRANT EXECUTE` |
| триггер | `CREATE OR ALTER TRIGGER` (с его состоянием ACTIVE/INACTIVE) | комментарий |

`DATABASE.sql` содержит `SET SQL DIALECT n`, кодировку по умолчанию (в виде комментария),
комментарий к базе данных и привилегии уровня базы данных (`GRANT CREATE TABLE TO …`,
`GRANT ALTER ANY PROCEDURE TO …`, `GRANT ALTER DATABASE TO …`).

Не выгружаются: системные объекты (`RDB$…`, индексы и триггеры, обслуживающие ограничения,
генераторы identity-столбцов), процедуры и функции пакетов (они находятся внутри тела
пакета), неявные привилегии владельца на собственные объекты, значения генераторов,
пользователи, shadow-копии. PSQL-объекты обёрнуты в `SET TERM ^ ;` … `SET TERM ; ^`; всё
остальное завершается `;`. Порядок вывода фиксирован (категории, затем имена), поэтому
повторные дампы одной и той же схемы совпадают байт в байт.

## Раскладка каталогов и имена файлов

Структура каталогов — это **данные, а не код**. В комплекте три пресета:

| Пресет | Куда попадает таблица `ACCOUNT` | Примечание |
| --- | --- | --- |
| `numbered` (по умолчанию) | `07_TABLES/ACCOUNT.sql` | Номера задают грубый порядок зависимостей при склейке файлов. |
| `plain` | `TABLES/ACCOUNT.sql` | Те же каталоги без номеров. |
| `flat` | `ACCOUNT.table.sql` | Всё в одном каталоге; тип — в имени файла. |

Всё остальное — TOML-файл: возьмите за основу пресет и измените то, что нужно:

```bash
fb-dump --layout plain --print-layout > my-layout.toml
```

```toml
base = "plain"                  # настроенный для запуска с
file = "{name}.sql"             # file-name шаблон; заполнители: {name}, {type}
database = "БАЗА.sql"           # файл на уровне базы данных

[dirs]                          # категория -> директория; "" корень директории, "/" Поддиректории
table  = "Таблицы"
index  = "Таблицы/Индексы"
view   = "Представления"
role   = ""

[files]                         # переопределение имен файлов для отдельных категорий
index  = "{name}.index.sql"
```

```bash
fb-dump -d DSN -o schema --layout my-layout.toml
```

Категории, которые вы не упомянули, сохраняют значения из `base`. Имена каталогов могут быть
любыми, какие принимает ваша файловая система, в том числе не латинскими; они должны
оставаться внутри дерева (никаких абсолютных путей и `..`). Имена объектов приводятся
к безопасному для файловой системы виду (разделители путей, запрещённые в Windows символы
и зарезервированные имена вроде `CON`).

Каждое дерево хранит свою действующую раскладку в **`.fb-dump.toml`**. Этот файл делает
дерево самоописываемым для любого потребителя, позволяет точечной выгрузке найти нужные
файлы, не зная раскладки заранее, и помечает каталог как принадлежащий fb-dump — непустой
каталог без него не будет тронут, пока вы не передадите `--force`.

## Гарантии

- **Полный дамп — всё или ничего.** Дерево собирается в промежуточном каталоге рядом
  с целевым и подменяется переименованием. Если хоть один объект не удалось прочитать,
  *ничего* не записывается, а код возврата — 3: наполовину записанное дерево выглядело бы
  в системе контроля версий как *удаление* объектов, то есть как ложная запись.
  `--allow-partial` отключает это поведение.
- **Ваш каталог в безопасности.** `--out` должен быть пустым, несуществующим или деревом,
  записанным fb-dump. Указывайте подкаталог репозитория, а не его корень.
- **Детерминированность.** Одна схема -> одни и те же байты. Никаких временных меток
  в выводе.
- **Только чтение.** fb-dump никогда ничего не делает с каталогом, кроме чтения.
- **Устойчивость на уровне объекта.** Один объект, который не удалось отрендерить (нет прав,
  странные метаданные), логируется и учитывается; он никогда не прерывает прогон. Коллекция,
  которую не удалось прочитать целиком, — инфраструктурная ошибка (код 1).

Транзакции — **read committed, record version, NO WAIT**: fb-dump никогда не ждёт на
блокировке. Как следствие, дамп — *не* снимок на момент времени: DDL, зафиксированный во
время выгрузки, может попасть в одни коллекции и не попасть в другие. Снимайте дамп, когда
схема не меняется.

## Коды возврата

| Код | Значение |
| :---: | --- |
| `0` | Успех. |
| `1` | Инфраструктура: не удалось подключиться, прочитать коллекцию или записать вывод. |
| `2` | Использование: неверные аргументы, неверный файл раскладки, не указана база данных. |
| `3` | Неполный результат: часть объектов пропущена или (в точечном режиме) часть имён не найдена. В полном дампе ничего не записано, если не указан `--allow-partial`. |

## Кодировки

Подключение открывается с `--charset` (по умолчанию `UTF8`). Для унаследованных баз,
метаданные которых хранятся в однобайтовой кодировке, её нужно указать явно, например
`--charset WIN1251`; иначе чтение завершится ошибкой декодирования и кодом 1.

В некоторых унаследованных базах метаданные хранятся в **смешанных** кодировках: одни строки
декодируются только как WIN1251, другие содержат символы вне WIN1251 и декодируются только
как UTF8. Одно подключение не может прочитать и то и другое, а firebird-lib загружает всю
коллекцию одним запросом, так что одна плохая строка валит всю коллекцию.
`--fallback-charset WIN1251` лениво открывает второе подключение и перечитывает такую
коллекцию через него; предупреждение называет каждую коллекцию, прошедшую этим путём.
Строки из резервного подключения читаются в другой транзакции, поэтому оговорка
о согласованности выше действует вдвойне.

## Воссоздание схемы из дерева

Дерево — это *описание*; превратить его обратно в базу данных — отдельная задача. Две вещи
требуют упорядочивания, которое одни лишь файлы выразить не могут:

1. **Зависимости между объектами внутри одной категории** — представление поверх другого
   представления, процедура, вызывающая другую процедуру, внешний ключ на таблицу, которая
   по алфавиту идёт позже. Нумерованные каталоги упорядочивают только *категории*.
2. **Гранты объектам PSQL** (`GRANT … TO PROCEDURE P`) требуют, чтобы получатель уже
   существовал.

Склейка файлов в порядке каталогов (`fb-dump -d DSN > all.sql` делает ровно это) работает
для схем без таких циклов; в общем случае используйте скрипт, применяющий файлы в порядке
зависимостей (или в несколько проходов) — для этого и нужен отдельный инструмент,
*применитель* (applier). Определения используют `CREATE OR ALTER` / `RECREATE` там, где
Firebird это поддерживает, так что повторное применение файла безвредно.

## Ограничения

- Не совпадает байт в байт с `isql -x`: firebird-lib форматирует DDL иначе (семантически эквивалентно).
- Нет снимка на момент времени (см. [Гарантии](#гарантии)).
- Комментарии к *параметрам* функций не выгружаются (firebird-lib не даёт для них `COMMENT ON`);
  параметры процедур, столбцы и комментарии ко всем объектам — выгружаются.
- Shadow-копии, BLOB-фильтры, пользователи и сопоставления (mappings) — не те объекты схемы, о которых знает fb-dump.
- Firebird 2.5 вне охвата (другой драйвер).
- Полный дамп читает часть метаданных объектов лениво; по медленному каналу большая база
  выгружается долго. Запускайте поближе к серверу.

## Разработка

```bash
uv sync --dev
uv run pyright fb_dump         # ожидается 0 ошибок
uv run pytest -q               # автономный набор тестов с контролем покрытия (≥ 80%; в настоящее время — ок 97%)
```

Тесты работают на заглушках (fakes) объектов firebird-lib — ни база данных, ни `fbclient`
не нужны. CI запускает и то и другое на каждый push; тег `vX.Y.Z` собирает автономные
бинарники.
